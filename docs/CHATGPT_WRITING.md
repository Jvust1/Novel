# Novel · ChatGPT 写作工作流

生效日期：2026-09-12。用户已明确选择：只用 ChatGPT，直接在聊天中写作，Novel 仓库保存规则、人物和进度。

## 从哪里开始

直接在 ChatGPT 对话中使用下面的项目指令，再提供当前故事档案和本章目标即可。不需要安装程序、配置模型或填写 API Key。

长期写作可在 ChatGPT 项目中放入项目指令和故事资料，使相关聊天使用同一组来源。项目资料需要实际上传或连接；仓库链接本身不代表正文已被读取。官方说明：[Projects and chats](https://learn.chatgpt.com/docs/projects)（核对日期：2026-09-12）。

当前仓库故事档案为 `writing/story_state.json`。它是空白起点，不代表已经有小说、大纲、人物或已接受章节。可先只告诉 ChatGPT：题材、主角、核心冲突和想要的文风；暂时没有答案的字段保持空白。

下载交付包中的 `Novel_故事档案.json` 是该档案的同内容副本；在 ChatGPT 中使用实际上传的文件名即可。

## 可复制的项目指令

```text
你是 Novel 项目的中文长篇小说共同作者。所有创作、规划、审校和记忆提取都在 ChatGPT 对话中完成。

开始前读取当前故事档案，并简短说明故事版本、上一章接受状态、本章目标和影响写作的缺失信息。只能使用实际读到的资料；没有访问文件的能力时，明确要求提供当前档案，不得假称读过 GitHub 或 Drive。

质量顺序：故事吸引力 → 人物可信度 → 情节因果 → 长篇连续性 → 语言自然度 → 有功能的环境描写 → 文风一致性。

1. 先理解总纲和人物，再给出场景计划。每场说明视角、目标、阻力、选择、代价、状态变化、信息释放和章末拉力。作者确认或修改计划后才写正文。
2. 人物只能依据其已知信息行动。叙述者知道、读者知道、某个角色知道是不同的事；秘密、未知与误解不得自动变成全员知识。
3. 情节由选择及后果推进，不能只因大纲要求就强行发生。对话须有目的、遮掩和人物差异。
4. 环境描写服务行动、情绪、信息、空间或节奏。允许短句、留白、不解释，减少重复心理说明和整齐的段尾总结。不要机械禁词。
5. Style DNA 使用可描述的句段节奏、视角、对白、词汇、情绪表达等特征。允许多来源融合，不借用参考小说长句；不要声称仅靠主观审读就完成了哈希重合检测。
6. 正文之后按连续性、人物、因果、语言和参考复用风险审校。指出短定位片段、原因和局部改法，保留有效段落；同一个 ChatGPT 的复核不等于独立外部评测。
7. 草稿、审校建议、未采用分支剧情均为候选。只有作者接受具体章节版本后，才为该版本提取记忆更新候选；作者确认记忆更新后再写入正式档案。
8. 锁定事实、人物知识和已经接受的历史不可被候选文本悄悄改写。矛盾先列出来；没有正文证据的推断标为待确认。
9. 每次只推进当前阶段。缺少关键创作决定时集中询问；已经确认的设定不重复索要。不得虚构作者确认、正文、评测或保存成功。
10. 换聊天前输出简洁交接包：当前版本、已接受章节、人物状态、开放伏笔、本章阶段和下一步，以及当前计划/草稿的版本及可读位置、未决审校问题和待确认记忆。工作中的草稿保持候选身份。正式恢复以确认档案为准，不依赖记住整段聊天。
```

## 故事档案与三层记忆

| 层级 | 放入本章的内容 | 边界 |
| --- | --- | --- |
| Canon | Story Bible、世界规则、锁定事实、明确禁用的剧情处理 | 缺少相关锁定约束时先补齐，不能静默省略 |
| Active | 出场人物、当前目标和知识、当前时间地点、近章摘要、开放伏笔、Style DNA | 只使用确认状态；说明这次选用了哪些人物和章节 |
| Recall | 与本章有关的历史事件、接受章节或短片段 | 按章节 ID 和版本引用；需要时读取，不默认塞入全文 |

`writing/story_state.json` 保存当前单部小说的 Canon、人物、Style DNA、摘要、事件、伏笔和进度。项目工程进度仍保存于 `governance/project_state.json`，两者不能混用。没有来源的空字段表示“尚未设定”，不表示已证明不存在。

## 每章怎么推进

1. **准备**：确定故事版本、本章编号、章纲、视角、字数偏好和本章禁揭信息。
2. **计划**：ChatGPT 输出场景计划；作者确认或调整。
3. **草稿**：按确认计划生成正文，标记 `chapter_id / draft_revision`，可继续在聊天中修改。
4. **审校与修订**：指出具体问题，局部修改并再次核对关键连续性。新修订对应新的版本。
5. **接受正文**：作者明确接受当前版本，例如“接受第 001 章 r2”。普通“继续”不代替章节接受。
6. **提取记忆候选**：只从接受的正文提取下方清单。作者可修改、拒绝或确认候选；有冲突时保留原正式状态。
7. **确认与保存**：将确认的记忆和进度作为一次连贯更新保存，故事 `revision` 加一。已接受正文的具体存放位置、版本和可用哈希写入章节记录；未知值保持空白。
8. **下一章**：使用更新后的确认状态准备下一章。若档案实际未保存，交接包标记待同步，不得宣称跨聊天已恢复。

记忆候选必须给出：

| 项目 | 必填内容 |
| --- | --- |
| 来源 | 故事基础版本、章节 ID、正文版本、作者接受状态 |
| 摘要与事实 | 简明摘要；事实的正文位置或短证据；确定/待确认状态 |
| 人物变化 | 人物、字段、旧值、新值、变化原因和证据；明确谁获得了什么信息 |
| 时间线 | 时间、地点、参与人、事件、因果关联；不明确的时间保持未知 |
| 伏笔 | 稳定 ID、埋设/推进/回收、相关章节；不能仅凭模型猜测宣布回收 |
| 冲突 | 与锁定设定、人物知识或既有章节的冲突，以及需作者决定的问题 |

保存时以 `chapter_id + draft_revision + 基础故事 revision` 对账：同一接受版本重复保存应无变化；旧版本不得覆盖新状态。修改已接受章节时另建修订，标记受影响的后续记忆待核对，不自动重写后续章节。此处是对话与归档协议，尚不是程序自动执行的事务或校验器。

## 版本与交接约定

`progress` 中的接受记录使用明确版本，不使用可被沿用的布尔开关：

```json
{
  "story_revision": 0,
  "chapter_id": "<当前章节 ID>",
  "plan_revision": "<作者确认的计划版本>",
  "draft_revision": null,
  "memory_update_id": null,
  "confirmed_by": "author",
  "confirmation_source": "<作者实际确认消息的位置或简短记录>"
}
```

上面仅是字段模板，未发生确认时，`plan_acceptance`、`chapter_acceptance`、`memory_acceptance` 均保持 `null`。正文接受记录必须填写正文版本；记忆接受记录还须填写对应的记忆更新 ID。不能由 ChatGPT 自行补造确认消息。

- 修改计划：递增计划版本，清空当前计划、正文和记忆的接受记录；旧正文只作待重新核对的候选。
- 修改正文：递增正文版本，清空当前正文和记忆的接受记录；旧记忆候选失效。重新核对与确认计划是否一致。
- 修改记忆候选：生成新的更新 ID，清空记忆接受记录，重新交作者确认。
- 基础故事 revision 改变：本章所有旧接受记录不得直接套用；先核对影响，再以新基础版本确认。历史接受记录保留在 `accepted_chapters` 及 Git 历史中。
- `plan_source`、`draft_source` 使用 `{ "revision": "...", "location": "...", "sha256": null }`。位置必须是当前对话实际可读的附件/文件/来源；哈希仅在实际计算后填写。计划可以保存在结构化项目资料中，正文仍遵守下方分工。
- 跨聊天恢复必须取得这些候选原件及未决审校问题；读不到时，将阶段标为 `awaiting_source` 并请求对应资料，不能仅凭一句摘要假称已恢复完整修订现场。

## 首次填写数组时的条目结构

以下是字段约定，不是已经存在的故事内容。ID 在同一故事内保持稳定；未设定的值用空值，不填猜测。证据 `source` 通常包含 `chapter_id`、`draft_revision`、`locator`；初始人物设定可用作者确认的设定文件或消息作为来源。

| 数组 | 每条至少保存 |
| --- | --- |
| characters | `id, name, identity, core_desire, current_goal, fear, flaw, self_deception, secret, speech, relationships, knows, does_not_know, false_beliefs, resources, status, recent_change, source`；知识/未知/误解每项均为 `{text, source}`，不得把叙述者知识复制给全部人物 |
| facts | `id, text, source, confirmation_status`；正式数组只放 confirmed 事实，候选留在 pending_memory_updates |
| chapter_summaries | `chapter_id, draft_revision, summary, source`，仅来自接受版本 |
| timeline | `id, time, place, participants, event, causes, source`；时间未知用 null |
| foreshadowing | `id, description, status, introduced_in, updated_in, source`；status 为 open / progressed / resolved，引用具体章节版本 |
| accepted_chapters | `chapter_id, plan_revision, draft_revision, base_story_revision, resulting_story_revision, chapter_acceptance, memory_acceptance, manuscript_source, memory_update_id`；修订追加记录，不覆盖旧接受记录 |
| pending_memory_updates | `id, base_story_revision, chapter_id, draft_revision, proposed_changes, conflicts, confirmation_status`；每项变化记 `target_id, field, old_value, new_value, source` |

字符/人名可以变化，稳定 ID 不随改名重建。用户拒绝候选或正文再修订后，相应候选不能进入正式事实、人物、时间线或伏笔数组。

## 一句话开始写作

```text
按 Novel 的 ChatGPT 写作工作流继续。请先读取当前故事档案；如果是空白起点，先帮我明确题材、主角、核心冲突和文风。已有档案则恢复到当前阶段。先给本章场景计划，等我确认再写正文；未经我接受的草稿不写入正式记忆。
```

## 保存分工与当前限制

- GitHub：写作协议、作者确认的人物与设定、结构化记忆、章节索引和进度。用户在本次对话中明确授权了人物与进度入库。
- 聊天、本地文件或 Novel 的 Drive 项目目录：小说正文、参考文本和原始资料。正文默认不提交代码仓库；归档遵循现有项目安全与同步规则。
- 文件更新能力以当前对话实际可用工具为准。没有写入工具时提供更新文件和待同步清单；不能宣称 ChatGPT 已自动写入 GitHub。
- 历史 Streamlit 和 provider 代码仍是旧原型，不是本工作流的启动入口。当前路线不运行 Ollama、不下载模型、不调用模型 API、不继续多模型路由或 API/OAuth 后端集成。
- 这次交付的是可直接使用的对话协议与空白状态档案；未替用户创建 ChatGPT 项目，未生成或接受真实小说章节，也未证明写作质量提升。
