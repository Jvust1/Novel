# 最终正文与审校证据一致性

这次解决的是实际写作链路中的错配：正文经过局部修订后，页面却仍展示初稿的质量、相似度或 AI 味报告。此前空白修订还会被复审，而最终正文又悄悄退回旧稿。现在三条入口共享同一套现有流程，所有最终诊断与实际交付正文绑定。

## GPT 写作入口保持不变

仍按 [GPT_WRITING_ENTRY.md](GPT_WRITING_ENTRY.md) 读取当前规则、实际私有故事状态、计划和正文。文件插件只提供文件能力；没有执行器，不声称跑了这些 Python 检查。对话中也应遵守同一原则：换稿后重新审校，报告明确指向该版本；旧稿的通过记录不能授权新稿；作者接受与记忆确认仍是另外两个明确步骤。

本候选分支是 `fix/final-output-gates-20261001`，接在冻结的 [Draft PR #49](https://github.com/Jvust1/Novel/pull/49) 上。#49 的源码、原创测试章与已交付档案保持不动，当前候选未合入 main。

## 复用现有流水线，减少分叉

- `NovelEngine.run` 先规划，再调用 `run_from_plan`
- `RoutedNovelEngine` 仍选择原有 writer/reviewer 角色，再调用同一个 `run_from_plan`，不偷偷改用写手审校
- 工作台“确认计划后写正文”也调用 `run_from_plan`，不会再规划一次或绕开这次确认的场景计划
- 初审、参考哈希检查、Story DNA/行为检查、人物口吻检查、外部 Hook、至多一次局部修订和复审都走同一条代码路径
- 快速草稿明确标记审校跳过，不调用 reviewer 或外部 Hook。修订/复审/Hook 失败就返回错误，不保存一个正文与通过记录不一致的新结果

`ChapterResult.initial_report` 保留初稿证据，`final_report` 保存当前稿证据；`final_review` 对应当前正文。原有 quality/similarity/AI-flavor/workflow 字段明确转为当前稿诊断。Voice 的旧 current/revised 字段为兼容保留，新增 final 视图，工作台显示 final 视图。

证据包含正文和场景计划的 SHA-256、阶段、实际输入指纹、审校是否执行及参考检查覆盖范围。独立留存的绑定还会拒绝正文、计划、复审或公开报告被修改后继续使用旧证据；清空或重写报告内的哈希不能自动降级成旧式无绑定结果。它是同一执行对象内的完整性检查，不是人类身份认证、不可伪造签名或跨服务信任系统。

## 不把不同检查混成“全书通过”

- Story DNA 与人物行为结构仍派生自场景计划，标记 `source=chapter_plan`。它没有自动抽取最终正文的事件链。局部修订不能偷偷修改已确认计划
- Voice 基线与历史 Story DNA 仍是调用者传入的资料，报告明确其来源未在此验证为“作者已接受正文的当前版本”。需要历史重建时继续对账，不能把算法版本号当成正文版本证据
- 默认参考保护只使用已有不可逆哈希。未配置的措辞/语义/事件序列比较明确标记未运行；分数 100 不代表原创性已被证明
- AI 味统计是编辑参考，不是 AI 检测器或作者接受门槛。不会机械洗稿、随机换词或保证通过检测
- 长度与场景结构诊断仍保留自己的范围；模型 pass 不是全部诊断已通过，更不是可发布结论。最终包的 `publishability_verdict` 保持空，作者接受保持待确认

模型与外部 Hook 的 pass 不能掩盖已列出的中/高等级问题；同一问题合并时保留更高严重性。非法 verdict/severity、缺少明确 issues 列表或损坏的 Hook 输出会报错，不自动变成“没有发现问题”。

## 明确的模型输出边界

现有 HTTPX 0.28.1（核实 15,524 星）提供真实传输入口的流式读取和关闭机制，完整 BSD-3-Clause 许可证与精确源码证据见 [来源说明](../third_party/httpx-output-boundary/NOTICE.md)。这是已有依赖 API 的实际接入，不是新搬入框架。两个 Python 环境的关键源码与提交 `26d48e0634e6ee9cdc0533996db289ce4b430177` 字节一致。

新的 `OutputPolicy` 为计划/正文/审校/修订/风格/记忆分别规定 8192/16384/8192/16384/4096/8192 个输出 token 的请求上限，可显式配置正整数；目标字数仍是独立软目标，不冒充实际 token 数。每段输出默认最多 1 MiB UTF-8；HTTP 响应体默认最多 2 MiB。超过额度时拒绝，不截断成候选。

HTTPX 请求明确选择 identity 编码，拒绝压缩响应后再读取，成功和错误响应都受 body 大小限制；这不是所有传输分配或进程内存的硬上限。Chat provider 必须提供 finish_reason=stop，拒绝 length、refusal、空白、null、意外工具调用或缺失完成原因。服务器若报告 token 使用量超过请求额度也拒绝；没有 usage 时不伪造计量证据。

仅明确说明 response_format 不受支持的 400/422 错误允许一次兼容回退。原输入、端点和输出额度不变；401/429/5xx、无关错误与传输故障不借此重试。旧服务器不提供完成原因、强制压缩或不支持受限调用时会明确失败，不自动退回无上限路径。真实端点兼容性仍需单独验证。

严格 JSON 复用 Python JSONDecoder/raw_decode、重复键检测、有限数值与 UTF-8 校验，之后仍交给 Pydantic 校验字段。只接受完整、无歧义对象及明确定义的代码块/简单前后说明；数组、多个对象、重复键、NaN/Infinity/溢出、未闭合结构会失败。不补括号、不剪掉尾部来伪造完整审校。已审阅 LangChain 的 partial-JSON 恢复实现，但其补全文本策略不适合这个门槛，未拷入。

## 可选 SDK 的真实边界

Instructor 使用带原始 completion 的接口并核对结构化结果，关闭自身重试。Outlines 必须明确选择适用后端的 max_tokens 或 max_new_tokens；不支持额度参数就失败，不捕获 TypeError 后偷偷去掉参数再调用。Guidance 同样传入明确额度。

这些可选 SDK 和 LiteLLM 本轮未安装，只有受控替身测试。SDK 可能已在内部缓存响应，Novel 的返回值字节检查不是 SDK 传输内存上限。Outlines/Guidance 的接口只提供完整 JSON/schema 证据，不提供 provider stop 证据。显式配置的多后端 fallback chain 是每次尝试受限，不是跨尝试总 token 或花费额度。没有新增下载、服务、凭据或真实模型调用。

完整输入上下文、选定 GPT tokenizer、跨模型窗口和调用费用仍未统一计量；本次输出额度不解决这些独立问题，也不允许裁掉必需 Canon、人物知识或风格参数来凑额度。
