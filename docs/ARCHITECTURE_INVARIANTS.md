# Architecture Invariants

这些原则除非有明确实验结果和 Decision Ledger 记录，不应被随意破坏。

## A1. 本地优先，云端模型可替换

UI、项目状态、章节、人物卡和 style fingerprint 默认保存在本地项目目录。模型调用通过 provider adapter，不绑定单一厂商。

## A2. 规划与写作分离

不能把“理解章纲、规划场景、写正文”压成一个自由生成调用。至少保留：

`Context → Scene Plan → Draft → Review → Repair → Memory Update`

## A3. 人物状态是一等数据

角色不仅有简介，还必须有动态字段：当前目标、情绪压力、关系、已知事实、未知/误解、秘密、资源、伤病/能力、最近状态变化。写作时人物知识边界属于硬约束。

## A4. 长篇记忆分层

- Canon：Story Bible、锁定事实、世界规则。
- Active：当前人物、当前地点、开放伏笔、近章摘要。
- Recall：完整章节与历史事件，按需检索。

不得用“把全文全塞进 prompt”替代记忆设计。

## A5. 情节必须通过人物因果推进

场景计划至少回答：谁想要什么、谁/什么阻止、人物做出什么选择、代价是什么、场景结束时什么状态发生不可忽略的变化。

## A6. Style DNA 可解释、可混合

风格不是一个作者名字。Style DNA 由多个可观察维度组成，并允许多来源加权。生成提示使用派生特征，不依赖长篇参考原文。

## A7. 环境描写有预算

环境只在以下至少一项成立时扩写：影响行动、提供信息、强化人物感受、建立空间关系、改变节奏、形成题材辨识度。否则压缩。

## A8. 写后审校必须局部修复

Reviewer 发现问题后优先定位问题段落并局部修订，不默认整章重写，以减少人物声线和细节随机漂移。

## A9. “去 AI 味”是统计 + 编辑问题

不靠一张绝对禁词表。结合重复模式密度、句长波动、段落均匀度、解释倾向、模板化情绪、修辞过密、角色同声等信号，并允许题材/作者偏好覆盖。

## A10. 用户原稿与参考文本不进入代码仓库

GitHub 保存代码、Schema、治理和派生特征；Drive 保存原始文件与重要产物。API secrets 永不持久化到仓库。

## A11. 参考文本用于“特征学习”，不是“句子借用”

系统需要保留非可逆 reference signature，用于检查长片段近似复用；如果输出与参考文本异常接近，应提示并重写。

## A12. 评测以真实章节为准

任何架构升级都要用固定样例做 A/B：情节吸引力、人物可信度、连续性、语言自然度、AI 味、参考重合风险。组件变多不代表质量变好。
