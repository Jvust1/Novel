# 工作台恢复编辑与真实大纲绑定

本轮修复两处实际界面反例。第一处：风格保存中断使页面提前停止，Streamlit 清理了没有渲染的写作控件；重新读取或重试后，手工计划、章目标和备注丢失，章节编号回到默认值。第二处：另一会话保存新大纲后，旧会话仍把两份旧缓存相互比较；刷新风格后，旧大纲可继续进入正文请求并被保存。

## 在现有工作台里如何恢复

- 风格保存失败、旧会话被阻止或等待重试时，现有项目字段继续保留，包括手工计划 JSON、章节编号、章目标、备注和发布草案。只保留当前进程会话中的编辑，不冒充已保存文件；关闭整个会话仍须自行保存
- 原有风格重试和重新读取仍走同一保存恢复机制，不重复分析，不认可正文或记忆。待恢复状态仍会阻止后续写作
- 已保存大纲变化时，先使用“重新读取已保存层级大纲”。该操作只读取当前磁盘大纲，不覆盖未保存的编辑 JSON，也不把旧计划改成已接受计划
- 核对新大纲后，重新选择并载入章节，编辑或重新生成场景计划，再明确点击按计划写正文。只刷新风格或大纲均不能复活旧绑定
- 若旧会话尝试保存其大纲编辑，而磁盘大纲已经变化，停止并保留两边内容；不会覆盖另一个会话的新设定。明确重新读取、核对差异后再决定保存的版本

## 每次实际使用来源都核对

大纲身份继续使用已有 JSON 内容指纹，不新增历史版本系统。载入章节、生成计划和写正文前检查真实已保存大纲，而不仅比较会话缓存。实际 HTTP 请求前及读取响应体后，再核对本次冻结的风格与大纲来源；格式降级的下一次请求同样检查。计划返回后、正文和计划文件发布前也再次检查。来源改变时不继续请求，不发布过期结果。

读取缺失、损坏或不符合现有结构的大纲时保留原件并报错。项目锁和单文件原子写入继续沿用 ProjectStore。保存大纲在同一锁内比较已加载来源与实际文件，再执行原写入；没有复制事务系统或新增服务。

无层级大纲绑定的原手工计划流程保持原样。人物、故事状态、作者接受及记忆确认仍按各自原有协议处理；恢复编辑不会制造新的接受记录。已存在的记忆候选在风格/人物/计划背景改变后仍需重新核对，不因界面字段恢复而跳过来源检查。

## 复用与边界

编辑保留采用 Streamlit 官方说明的[中断控件清理方法](https://docs.streamlit.io/develop/concepts/multipage-apps/widgets#option-3-interrupt-the-widget-clean-up-process)：在渲染前通过公开 Session State 接口保留已有项目字段。沿用本项目现有字段集合和切书机制，不新增第二份草稿缓存，不持久化模型凭据。实际来源检查复用原 provider request_guard、ProjectStore 原生项目锁、JSON 校验和大纲指纹。

本轮安装环境为 Streamlit 1.64.0；未更改依赖或复制上游源码。公开上游 [streamlit/streamlit](https://github.com/streamlit/streamlit) 在 2026-10-01 21:27 UTC 只读核对为 Apache-2.0、45,872 stars；星数只是当时观察，不是本项目质量证明。现有 boltons 等源码 pin 与完整许可保留。

这是本地合作会话的恢复和来源核对，不是恶意文件竞态沙箱、任意多文件原子事务、Drive 保存协议或作者身份认证。普通 GPT + GitHub 插件入口不要求运行本地工作台；没有实际执行器时按文本协议对照真实私有来源，不声称已经运行这些校验。原预算、已接受历史、记忆确认和所有质量门保持。
