# 第一章预检的身份与指纹检查

本次修复一个可复现的窄问题：故事还没有已接受章节、revision 为 0 时，`preflight_next_chapter_context` 的空历史分支跳过了调用者明确提供的故事身份和历史指纹检查。对书 B 传入期望书 A，直接 API 原来仍返回 `blocked=false`；真实 `next-preflight` 命令传入错误历史指纹也会退出 0。

现在即使没有接受历史，显式期望仍会核对。不匹配抛出既有 `StateError`，命令行返回 2，不返回可以继续写作的上下文，也不修改故事文件。CLI 的故事身份原来就由实际 `load_state` 检查，本次保留这道检查。

## 哪些调用保持原样

- 省略期望值或显式传入 `None`，维持原有正常流程；仍执行必需来源、上下文预算和候选隔离检查
- 正确故事身份与正确空历史指纹，得到与未传期望时完全相同的预检结果
- 空字符串、错误故事、错误指纹及其他显式不匹配值不会被当成“没有要求检查”
- 第一章空历史的原输出与指纹算法不变；不增加接受章节，不捏造作者确认，不改变审校、记忆或保存流程
- 已有接受历史及日志所属续写维持原有身份、来源、读回和预算门禁，不借此开放空档案的接受历史续写

## 指纹来自哪个入口

`next-preflight` / `preflight_next_chapter_context` 返回 `accepted_history.accepted_history_sha256`。明确希望核对这份预检身份时，使用该入口实际返回并已保留的值，不编造哈希，也不在提交旧请求前偷偷换成最新值。

revision 为 0 时，`accepted-history` / `rebuild_accepted_history` 的历史重建指纹与第一章预检的空历史指纹原本不同；这项既有兼容性保持不变，两者不能混用。已有接受章节的路径仍使用原历史重建机制。

## 在 GPT 对话中的边界

GitHub 插件能读规则不代表已经执行预检。只有实际读取私有故事来源并运行程序后，才报告程序校验和 CLI 结果；无执行器时按原对话协议核对书名/故事身份、接受版本、计划与来源，并明确程序检查未运行。真实作品继续放在作者指定的私有位置。

此修复复用既有 Pydantic 状态验证、历史身份逻辑和 `StateError`/CLI 错误通道，只增加显式期待值比较，没有另建历史系统、添加依赖、请求模型、改写档案或自动接受内容。工程校验不认证作者，也不证明文学质量。

独立原始复现的三个反例在修复后通过：直接 API 错书、直接 API 错指纹、实际 CLI 错指纹。回归还锁定完整默认输出、正确指纹、缺少必需来源、预算不足及重拟计划后的旧候选隔离。精确矩阵与发布收据见 [候选记录](../governance/initial_preflight_candidate.json)。
