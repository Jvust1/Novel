# 历史来源相同标识下的冲突检查

历史自动补入原来只看 `source_id + revision` 是否已经出现，然后跳过后来的来源。真实合成复现中，两章都明确接受、各有实际文件，却都使用 `draft@1` 这个标识；默认续写只带入第一章正文，静默漏掉第二章，预算仍很充足。直接预检或 CLI 里，同标识但不同位置/字节的输入也能挤掉已接受原稿。

本次在原历史合并边界核对既有完整来源指纹。同标识且完整来源一致，才沿用已有的一份；同标识指向不同位置、文件身份或正文摘要时，明确停止并要求核对。不会自动选较旧/较新一份、改来源编号、删冲突记录或重写已接受稿。

## 怎样区分正常复用与冲突

- 比较仍使用原 `source_fingerprint` 和经过 Pydantic 校验的 Artifact。正文必须符合它声明的完整 UTF-8 摘要；位置、文件身份、版本等原有来源字段一并绑定
- 明确传入的一份已接受原件与自动补入原件完全一致时，不重复加入，原 priority/required 语义保持
- 两个自动补入的已接受来源发生同标识冲突，或者明确提供的来源与自动补入来源冲突，都不再静默跳过
- 明确输入列表中的重复 ID/版本仍沿用原拒绝规则，不因字节相同而放宽
- 输入来源先形成独立快照，再校验和组装；调用者随后修改自己的字典，不会让通过核对的版本与实际拼入的版本不同

冲突不是“可选历史超预算”。即使当前预算很小，已经参与本次合并的身份冲突也不能被悄悄当作省略。正常无冲突的来源仍按原预算规则完整纳入或明确列出省略原因。

## 对已有档案的影响

故事档案、已接受正文、接受证据和历史指纹均不因此改写。存在歧义的档案仍能保留并供核对，但不能把不一致的来源当成同一份原稿进入这条预检/续写请求。须核对真实来源与版本，按作者明确选择处理；不要伪造新 ID 或接受回执以绕过检查。

作用范围是本次明确输入及所选择的自动历史片段。`history_source_limit` 仍是调用者明确选择的原功能：0 不自动加入历史全文，较小值限制所取的最近片段；它不是自动修复冲突的办法，也不证明未选择的材料已完成全局审计。完整历史派生区、来源绑定、作者当前计划和预算通道仍保留。

普通档案与作者日志通过同一个历史合并函数进入各自既有的预检和受控续写路径。冲突必须在发出模型请求前停止；不消耗一次模型调用来“试试看”，不产生替代正文或改变记忆。任意外部 Artifact 不能直接传给受控档案适配器；该适配器的真实缺口是多个已接受章节自身的标识冲突。

## GPT 插件与执行边界

GitHub 插件读取规则不代表执行了校验。只有真实读到所选私有原件，并在实际执行器中运行后，才能报告程序核对/CLI 结果。没有执行器时，继续按对话协议对照作者已接受版本、来源位置和实际正文，明确标注未运行程序；不要求用户安装本地界面，不把私人小说复制到公开仓库。

本修复只复用已有来源指纹、Artifact 验证与错误通道，没有新增历史系统、模型框架或依赖，也不认证作者身份、自动解决来源冲突或证明文学质量。实际验证与兼容控制见 [候选记录](../governance/history_source_identity_candidate.json)。
